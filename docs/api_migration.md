# DBonk スクレイパー API化 移行計画

## 背景

現在の `src/scraper.py` は `body.innerText` の正規表現パースと、テキストに基づく
ヒューリスティックなクリック操作で動いている。DBonk のUI・文言変更に弱く、
1,443行のうち大半がその防御コードになっている。

DBonk のページ（`https://dbonk.com/bdmbsmv2/index.php`）は画面遷移なしで
「Loading Data」表示のあとにデータが差し込まれる作りのため、内部的には
XHR/fetch でJSON等を取得している可能性が高い。ブラウザが受け取るその
レスポンスを直接使えば、以下が期待できる:

- 画面文言・レイアウト変更の影響を受けない安定した取得
- スクロール・クリック探索・待機ループの大部分が不要になり大幅に高速化
- 将来的なヘッドレス化

## ステップ1: API調査（次回の実取得時に1回だけ実行）

キャプチャ機構は実装済み。**通常の取得を1ギルドだけに絞って**、次のように実行する:

```powershell
# config/guilds.txt を一時的に1ギルドだけにしてから
.\.venv\Scripts\python.exe -m src.scraper --capture-api data\api_capture
```

- 通常どおりログイン→ランキング→ギルド詳細まで進めば、その間にサイトが叩いた
  XHR/fetch レスポンスが `data\api_capture\` に保存される。
- 取得動作そのものには一切影響しない（キャプチャ内の例外はすべて無視される）。
- 終わったら guilds.txt を元に戻す。

### 出力の見方

- `index.jsonl` … 1行=1レスポンス。`url` / `method` / `status` / `content_type` /
  `post_data`（POSTの場合の送信内容）/ `body_file`（本文の保存先）。
- `NNNN_xxx.json` / `.txt` … レスポンス本文。

### 調査で確認すること

1. **ギルドランキング一覧**を返すエンドポイントはどれか
   （検索文字列がクエリ/POSTに入るか、全件返してクライアント側で絞るか）
2. **ギルド詳細（メンバー一覧・サマリー・拠点戦履歴）**を返すエンドポイントはどれか
   （ギルドIDの形式、1リクエストか複数か）
3. 認証方式（CookieセッションだけでAPIが叩けるか、トークンが要るか）
4. レスポンス形式（JSONか、HTMLフラグメントか）

## ステップ2: 移行の設計方針（調査結果が出たら実装）

侵襲を最小にする2段階で移行する:

### 2a. レスポンス傍受方式（推奨・先行実装）

ブラウザ操作は現状のまま残し、**パースだけ**をAPIレスポンスに置き換える。

- `page.expect_response(url_pattern)` でギルド詳細クリック時のAPI応答を受け取り、
  `parse_members_from_blocks` / `parse_summary_metrics` / `parse_node_history_rows`
  の代わりにJSONから直接組み立てる。
- スクロール待ち（`scroll_until_member_section`）・`wait_for_active_members_ready` が
  不要になる。
- ログイン・画面遷移は既存コードを使うので、認証問題が発生しない。
- 失敗時は現行の innerText パースへフォールバックできる形で実装する。

### 2b. API直叩き方式（将来）

調査でCookieセッションだけで叩けると分かったら、Playwrightの
`context.request.get/post` でランキング→各ギルド詳細を直接リクエストする。
ブラウザ描画が不要になり、実行時間を大幅に短縮できる見込み
（現在: 34ギルドで約2時間 → 期待値: 数分）。

## 進め方

1. 次回収集時に `--capture-api` 付きで1ギルド取得（ステップ1）
2. `data/api_capture` の中身を確認し、エンドポイント対応表をこのファイルに追記
3. 2a を実装（既存パーサーはフォールバックとして残す）
4. 数回の実運用で安定を確認後、2b を検討
